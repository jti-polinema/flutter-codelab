Bahasa Indonesia | English

Last week, you automated checks and produced an app artifact. Now you will prepare a limited beta release, collect feedback, and monitor crashes and feature usage after release.

Learning objectives

  • explain the path from a release candidate to beta testing;
  • prepare an app version and Android App Bundle (AAB) for internal testing;
  • configure Firebase Crashlytics and Analytics for testing;
  • review release signals and decide what to do next using evidence;
  • use AI responsibly when analyzing logs.

What you need

  • A Flutter project that builds and has passing tests.
  • A Git repository and access to the CI pipeline from the previous week.
  • A Firebase project for Android; prepare Google Play Console access if available.
  • An Android device for beta testing. Do not use production data.

Note: Internal distribution is still an app release. Use invited testers, protect signing keys, and do not put personal or secret data in logs.

1. From CI to beta release

The CI pipeline from last week produces a checked build. To test it with a limited audience, create a traceable release candidate, distribute it through a testing track, and observe the results.

  1. Confirm that the candidate commit passes analysis and tests.
  2. Increment the build number and create a release AAB.
  3. Upload the AAB to an internal testing track and invite testers.
  4. Collect relevant reports, crashes, and usage signals.
  5. Reproduce issues, fix them, and decide whether to continue the release.

2. Testing tracks

Google Play provides testing tracks for different audiences and processes. Internal testing is suitable for initial checks by a small group. Account requirements and Play Console processes can change; follow the latest instructions in the console.

If Play Console access is unavailable, use Firebase App Distribution to distribute a private test build. Document the service and its limitations.

1. Record the version and commit

In pubspec.yaml, a version such as 1.0.0+21 specifies app version 1.0.0 and build number 21. Increment the build number for every new upload. Link the candidate to a Git commit or tag and describe changes/limitations in the release notes.

2. Run checks and build

flutter pub get
dart format --output=none --set-exit-if-changed .
flutter analyze --fatal-infos
flutter test
flutter build appbundle --release
  • Confirm analysis and tests pass on the commit to be released.
  • Review release and signing configuration using Flutter documentation.
  • The AAB is usually created under build/app/outputs/bundle/release/.
  • Keep the AAB with its commit notes and CI results; do not share it publicly.

Never put a keystore, password, or token in the repository or logs. Do not treat values compiled into an app as secrets.

1. Play Console

  1. Create or select an app in Play Console, then open the Internal testing track.
  2. Add testers through an allowed email list or group.
  3. Create a release, upload the AAB, add release notes, and review any warnings.
  4. Start the internal rollout and share the opt-in link only with testers.
  5. Ask testers to install the app and check key flows on their devices.

2. Private distribution alternative

If you do not have Play Console access, use Firebase App Distribution or another instructor-approved private method. Record the testers and build version. This alternative still requires installation and testing evidence.

3. Record evidence

For each report, write down the version/build, device and OS, reproduction steps, expected result, actual result, and sanitized evidence. Never ask testers to send credentials or personal data.

1. Set up Firebase

Follow the official FlutterFire guide to connect the app to Firebase. Add the packages below and complete platform configuration before initializing Firebase:

flutter pub add firebase_crashlytics firebase_analytics
flutterfire configure

Register error handlers after Firebase.initializeApp(), for example near the start of main():

Import dart:ui for PlatformDispatcher, along with the Firebase packages used below.

FlutterError.onError =
    FirebaseCrashlytics.instance.recordFlutterFatalError;
PlatformDispatcher.instance.onError = (error, stack) {
  FirebaseCrashlytics.instance.recordError(
    error, stack, fatal: true,
  );
  return true;
};

Follow Firebase documentation for imports, Gradle configuration, and current platform steps. Verify a test error appears under the correct version in the Crashlytics dashboard.

2. Log a non-sensitive event

await FirebaseAnalytics.instance.logEvent(
  name: 'beta_feedback_sent',
  parameters: {'screen_name': 'home'},
);

Log actions that help evaluate the app, not form contents, email addresses, tokens, or personal identifiers. Document event and parameter meanings.

Test fatal crashes only on a test build/device. Avoid sending personal data to Analytics, Crashlytics, or AI.

1. Verify telemetry

  1. Run the test build and trigger a planned, non-sensitive Analytics event.
  2. Send one synthetic non-fatal error to confirm Crashlytics receives a report.
  3. To test a fatal crash, follow official test instructions on a test device only.
  4. Wait for processing, then check the event, app version, device, and stack trace.
  5. Confirm the report contains no credentials or personal data.

2. Monitor and triage

Compare crash-free users/sessions, new issues, affected users, versions, and tester reports. Aggregate data is a signal, not standalone proof of root cause. Reproduce the bug and match it with a stack trace before drawing conclusions.

If an issue affects a key flow or creates user risk, stop expanding distribution and follow the track stop/rollback procedure. Record the reason, evidence, owner, and fix version.

3. AI and logs

Before asking AI to analyze logs, remove tokens, email addresses, user IDs, private URLs, and sensitive payloads. Ask for hypotheses with evidence and reproduction steps; verify the result against code, tests, and a device.

Assignment

  1. Prepare a beta candidate with a recorded version/build number, commit, AAB, and check results.
  2. Distribute it through Internal testing or Firebase App Distribution and test it on a device.
  3. Configure Crashlytics and one non-sensitive Analytics event; verify them in the dashboard.
  4. Create docs/release-report.md with distribution evidence, test results, findings, impact, decisions, and next steps.
  5. Record any AI usage, sanitized log context, and how AI suggestions were verified.

If service access is unavailable, document an alternative demonstration and its limitations. Do not claim dashboard or distribution evidence that was not actually produced.
